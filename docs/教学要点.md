# AI 与 Agent 原理演示平台 · 教学要点

> 本文件是**讲解材料**，与演示页面完全解耦。页面只保留可操作的控件（章节、问题、能力开关、画布、时间线），
> 所有教学目标、观察重点、操作顺序、概念解释都放在这里，便于讲师按需修改、打印或单独分发。
>
> 配套平台：本地启动后访问 `http://127.0.0.1:8787`。

## 零、讲解主线

一句话：**先暴露局限，再引入能力，用同题对比证明差异，最后解释原理。**

```
LLM 只会读你给它的文字   →   Prompt 只改说法，不改能力
        ↓
它不记得上一轮           →   应用替它保存历史，再重发一遍
        ↓
它拿不到企业数据         →   Function Calling：模型提请求，程序去执行
        ↓
工具接入方式五花八门     →   MCP：把工具声明标准化
        ↓
内部制度它不知道         →   RAG：检索到的片段进上下文
        ↓
每次分析方法不稳定       →   Skill：把「怎么分析」沉淀成按需加载的方法
```

讲解节奏建议：每章 4–6 分钟，**先运行、后解释**。不要先讲概念再看结果，否则听众会把结果当成动画。

## 第一章 · 什么是 LLM

> **一句话主旨**：模型只看得见你发给它的文字

**教学目标**
理解 LLM 是一个「根据你提供的上下文生成文字」的模型服务，不是天然连接了所有业务系统的程序。

**演示问题**
请分析一家营业收入下降 20%、经营活动现金流为负的企业可能存在什么风险。

**观察重点**
回答通顺、结构完整，但没有任何一处引用企业级数据来源。这说明流畅不等于掌握事实。

**现场操作顺序**
1. 先不要开启任何能力，直接点击「运行」。
2. 观察画布：此刻只有「用户 → LLM → 用户」这一条通路。
3. 再追问一句：星河科技有限公司的注册资本是多少？
4. 对照两次回答，判断哪些是推断、哪些是数据。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| LLM | 根据输入的上下文，逐个预测下一个 Token 的模型服务。 |
| 上下文 | 本次调用中模型能看到的全部文字，除此之外它一无所知。 |
| 幻觉 | 当上下文里没有可靠依据时，模型仍可能生成看似合理的内容。 |

**讲师提示**：如果听众追问「它是不是偷偷查了数据库」，直接打开「详情 → 构建模型请求」，把他看到的全部内容展示出来——只有那段文字。

## 第二章 · Prompt 与 System Prompt

> **一句话主旨**：指令改变输出方式，但不新增能力

**教学目标**
理解 System Prompt 与 User Prompt 的作用边界：它改变模型「怎么答」，不改变模型「能拿到什么」。

**演示问题**
请用以下三个指标分析企业风险：2024 年营业收入 1000 万元，2025 年营业收入 800 万元，2025 年经营活动现金流量净额为 -100 万元。

**观察重点**
回答变得更规范、更克制，但模型仍然只掌握你粘贴的三个数字——指令没有联网能力。

**现场操作顺序**
1. 先在不开启 System Prompt 的情况下运行，观察回答的组织方式。
2. 打开「System Prompt」开关，点击旁边的「查看」确认内容。
3. 再次运行，对比两次回答的结构差异。
4. 注意：两次回答的数据来源完全相同。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| System Prompt | 以 system 角色发送的指令，用于约束角色、口径与输出结构。 |
| User Prompt | 用户当前这一轮的输入内容。 |
| 边界 | Prompt 是「要求」，不是「授权」，更不是「能力」。 |

**讲师提示**：可以现场删掉「不得编造未被提供的财务数据」这句，再跑一次，让听众看到输出立刻变松。这是最有说服力的一步。

## 第三章 · 上下文与多轮对话

> **一句话主旨**：模型不记得你，记得你的是应用

**教学目标**
区分「上下文」「会话历史」「长期记忆」，理解多轮对话的本质是应用把历史重新发一遍。

**演示问题**
第一轮：某企业 2024 年营业收入 1000 万元，2025 年营业收入 800 万元。
第二轮追问：那它的收入下降了多少？

**观察重点**
开关关闭时，第二轮请求里只有当前这句话；打开后，历史消息被重新发送给模型。所谓记忆，是应用在替你记事。

**现场操作顺序**
1. 保持「多轮上下文」关闭，先发送第一句话。
2. 在下方追问框输入：那它的收入下降了多少？
3. 观察模型是否知道「它」指的是哪家企业、哪两个数字。
4. 打开「多轮上下文」，重复上面两步。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| 上下文 | 本次调用实际发送给模型的全部消息。 |
| 会话历史 | 应用保存的对话记录，是否发送由应用决定。 |
| 长期记忆 | 跨会话持久化并按需读取的信息，更不是模型自带的。 |

**讲师提示**：时间线里的「构建模型请求」会写明本次发了几条消息。关闭时是 2 条（system + 当前问题），打开后变成 4 条。数字比比喻更有力。

**讲师提示（多轮时间线）**：连续问几次不会被覆盖。执行时间线会保留历次对话，按「第 1 次 / 第 2 次」分段，每段有自己的颜色；
顶部的「全部 / 只看本次」可以切换。讲「历史有没有真的发出去」时，直接点第一轮里那条「构建模型请求」，
对照后面的轮次，能看出消息条数在变多。这比口头解释「应用在替你记事」更有说服力。

## 第四章 · Function Calling 工具调用

> **一句话主旨**：模型提出请求，程序决定执行

**教学目标**
理解模型如何获得外部数据访问能力，以及「模型请求 / 应用执行 / 工具访问」这三者的分工。

**演示问题**
请查询演示企业A（星河科技，DEMO001）的注册资本和登记状态。

**观察重点**
模型并没有「打开数据库」，它只是输出了一段结构化的调用请求；真正查数据的是应用调用的工具程序。

**现场操作顺序**
1. 关闭工具，直接运行，观察模型是拒答、编造，还是明确说明无法获取。
2. 打开「工具调用」，并勾选「企业工商信息查询」。
3. 再次运行，点击画布上的工具节点，查看模型提出的参数与实际返回。
4. 再看时间线：模型请求 → 权限校验 → 工具执行 → 结果回传 → 生成回答。
5. **点「查看本次实际发送给 LLM 的完整工具 Schema」**：先看「工具清单」里每个工具的 JSON Schema，
   再切到「完整请求体」，看这份 `tools` 数组是怎么和 messages 一起发出去的。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| Function Calling | 模型输出结构化的工具调用请求，由应用解析并执行。 |
| 分工 | 模型决定请求什么，应用决定是否执行，工具负责真实访问数据。 |
| ≠ 代码执行 | 模型不能直接执行任意代码，它只能提出请求。 |
| 工具不是装进模型里 | 每次请求都把 `tools` 数组作为 API 参数发过去，模型只在「这次给的清单」里选。 |
| schema 就是说明书 | `description` 写得含糊模型会调错，`parameters` 没写清模型会给错参数。 |
| schema 也占上下文 | 工具越多、说明越长，输入 token 越多。挂几十个工具不是「能力更强」，是「更贵更乱」。 |

**讲师提示**：一定要点开时间线里「模型请求工具」那一步，让大家看见 `tool_calls` 只是 JSON。这是全章最关键的一屏。

**讲师提示（工具 Schema 面板）**：这一屏专门用来打掉一个常见误解——「工具已经被装进模型内部了」。
打开面板指着 `tools` 数组说：这就是完整内容，它随每一次请求发送，不勾选就没有。然后关掉工具再运行一次，
回到面板看「本次请求不带 tools 参数」，模型就只能凭记忆答。前后对比一次，比讲十遍定义都清楚。

## 第五章 · API 与 MCP

> **一句话主旨**：换的是接入方式，不是模型智力

**教学目标**
理解 MCP 解决的是「AI 应用与外部工具之间的标准化接入」，而不是让模型更聪明；同时分清
**Function Calling（模型怎么提请求）** 与 **MCP（请求由谁执行）** 是两件不同的事。

**演示问题**
请查询宁德时代新能源科技股份有限公司的工商登记信息：注册资本、登记状态、法定代表人。

**观察重点**
画布上会先出现 MCP Client，再出现「天眼查」这个 MCP Server 节点；回答里的统一社会信用代码、注册资本、法定代表人
都是外部实时返回的，不是模型编的。MCP 的价值在接入侧：工具清单由 Server 声明，应用无需硬编码，换工具不改代码。

**这一章必须先纠正的一个说法**
不要说「通过 MCP 接入，就是把同名能力的调用通道切到 MCP Server」。这个说法会让人以为 MCP 是 Function Calling 的
升级通道。正确的关系是：

```
Function Calling                MCP
模型怎么提出调用请求             请求由谁执行
（API 参数 tools + tool_calls）  （一种标准化的执行与声明协议）
        └──── 两者互相独立，可以只用一个，也可以一起用 ────┘
```

同一个「查企业工商信息」能力，可以有两种并列的执行路径：

| 路径 | 谁在执行 | 走什么协议 | 什么时候选它 |
| --- | --- | --- | --- |
| ① 本地函数直接执行 | 应用自己进程内的函数 | 不经过网络 | 逻辑简单、数据在应用内、要求最低延迟 |
| ② 通过 MCP Server 执行 | 独立进程 / 内网系统 / 云端服务 | JSON-RPC（stdio 或 Streamable HTTP） | 工具要跨团队、跨系统复用，或由外部统一维护与审计 |

模型对这两条路径**没有感知**：它拿到的都是一份 `tools` 清单，输出的都是一段 `tool_calls`。
区别只发生在应用侧——请求交给谁去跑。

**本平台已接入的真实 MCP 服务器**
| 服务器 | 传输 | 工具数 | 说明 |
| --- | --- | --- | --- |
| 演示工商库（本地） | stdio + JSON-RPC | 1 | 虚构企业，用于与真实数据对照 |
| 同花顺 iFinD · 证券数据 | Streamable HTTP | 9 | 行情、财务指标、公告与新闻检索 |
| 同花顺 · 快查企业 | Streamable HTTP | 2 | 企业工商、股权类查询 |
| 同花顺 · 法规库 | Streamable HTTP | 6 | 法规与条款检索 |
| 天眼查 · 企业数据 | Streamable HTTP | 17 | 工商画像、风险、股权、知产等 |

**现场操作顺序**
1. 先在「能力 → 工具调用」里**只勾本地函数**（企业工商查询），运行一次，记住回答与画布结构：
   画布上是「工具处理器 → 企业工商查询」一跳，进程内直接执行。
2. 换成勾「天眼查」的 search_companies 与 get_company_basic_profile，运行，观察画布最右列出现服务器节点，
   中间多出 MCP Client 一跳。
3. 点时间线里的「MCP tools/call：天眼查 / search_companies」，看参数与真实协议往返。
4. 对比两次的「工具请求」与「工具返回」：**模型侧的结构完全一样**，差别只在执行端与数据真实性。
5. 可以用「本地演示：同名工具改走 MCP」这个对照开关再演示一次：同一个 get_company_info，输入输出不变，
   只是执行端从本地换成了 MCP Server。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| Function Calling | 模型通过 API 参数拿到工具清单，输出结构化调用请求。与 MCP 无关。 |
| MCP | 模型上下文协议，标准化声明与调用工具、资源、提示模板。管的是「执行与发现」。 |
| 两者关系 | 并列而非替代：Function Calling 决定「模型能不能提请求」，MCP 决定「请求交给谁执行」。 |
| 两种传输 | 本地进程用 stdio（行分隔 JSON-RPC）；远程服务用 Streamable HTTP（POST + SSE，带会话 id）。 |
| 工具命名空间 | 平台把工具名写成 `服务器__工具`，模型看到的名字能唯一，面板也能说清工具来自谁。 |
| 别误读 | MCP 不是更强的推理能力，不是某个厂商的私有插件，也不是 Function Calling 的前置条件。 |

**讲师提示**：这一章最容易出问题的是额度。天眼查正式期免费档每天只有 10 次调用，演示前先用「MCP 服务器 → 测试」确认
额度还在；如果被限流，答案会如实报错，不会伪造数据。切到「同花顺 iFinD」或本地演示服务器可以继续讲。

**讲师提示**：如果被问「那上 MCP 有什么意义」，回答三句：工具清单自动发现、换工具不改应用代码、权限与审计可以在一个网关收口。不要说「更聪明」。

**讲师提示**：如果被问「那是不是所有工具都该走 MCP」，回答：不是。工具在应用内、调用频繁、延迟敏感时，本地函数更合适；
只有当工具需要跨系统复用、由外部团队维护、或必须统一审计时，MCP 的接入成本才划算。

## 第六章 · RAG 与外部知识库

> **一句话主旨**：回答的依据可以来自文档，而不是参数

**教学目标**
理解检索增强生成：把外部文档切片、建索引、按问题检索，再把片段放进上下文。

**演示问题**
怎么判断一家公司还不还得起债？请按知识库里的口径回答。

**观察重点**
这个问题在知识库里没有原句，但有一节叫「偿债能力指标」。只做词法匹配时，排名第一的是「一、总体原则」（因为命中了
"公司""判断"这些字）；换成向量检索，第一名的才是真正相关的「二、偿债能力指标」。这一屏能讲清"字面命中"与"语义相关"的差别。

**知识库当前规模**
8 篇虚构文档、61 个分块，覆盖授信政策、财务分析、行业关注点、贷后监控、担保管理、准入尽调、台账问答、风险提示规则。
每个分块都带来源文件与标题，界面上可以逐层展开：

```
server/knowledge/*.md  →  按 # 标题切分（单块 ≤ 320 字）  →  BM25 倒排索引 + 向量索引
                       →  按问题召回 TopK              →  拼成 system 消息注入
```

**现场操作顺序**
1. 先关闭知识库检索运行一次，观察模型给出的是通用经验还是本行口径。
2. 打开「知识库检索」，模式选「词法」，运行；再切到「向量」运行一次，对比 Top1 是否变化。
3. 点「查看知识库」：左侧文档树 → 展开 → 点某个分块，右侧能看到原文、分词结果（中文二元组）和向量前 10 维。
4. 在下方「检索测试」里输入同一句话，对照融合分、词法分、向量分与两个排名，再看「最终拼成 system 消息的内容」。
5. 注意回答里的口径来自这些文档，不是模型记住的。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| RAG | 检索 → 组装上下文 → 生成，参数没有被修改。 |
| 分块 | 文档按标题与句号切开，块太长会稀释相关性，太短会丢上下文。 |
| 词法检索 | BM25 统计词频与逆文档频率，只认字面重合，同义词与改写问法容易漏。 |
| 向量检索 | 用 Embedding 模型把文本映射为 1024 维向量，按余弦相似度召回，能处理同义与改写。 |
| 混合检索 | 两路分数各自归一化后加权：融合分 = 0.6 × 向量分 + 0.4 × 词法分（权重可调）。 |
| 向量缓存 | 向量按「模型 + 文本」哈希缓存到 data/index/embeddings.json，换模型自动失效，不重复计费。 |
| ≠ 训练 | RAG 不更新模型权重，改文档即改答案依据。 |

**这一章最容易出问题的地方**
- Embedding 没配好时，界面会明确显示"未配置，检索降级为词法匹配"，不会把词法结果说成语义理解。
- 换 Embedding 模型后第一次检索会重建索引，61 个分块大约 7 批请求，需要等几秒。
- 检索命中不等于内容现行或适用。演示时要主动说：文档是虚构的，真实制度要接行内知识库并做版本管理。

**讲师提示**：不要回避 BM25 的局限。主动做一次词法与向量的对比，反而更容易建立信任——银行场景里，过度承诺比能力不足更危险。

## 第七章 · Skill 与专家经验

> **一句话主旨**：把「怎么分析」沉淀成可复用的方法

**教学目标**
理解 Skill 不是一个巨大的说明书，而是一个**能力包**：主指令只做路由，方法论拆进 `references/`，
确定性计算放进 `scripts/`，模板放进 `assets/`，按需取用。也就是**渐进式披露**。

**演示问题**
根据以下数据分析企业风险：2024 年营业收入 1000 万元，2025 年营业收入 800 万元；2025 年总资产 1000 万元、
总负债 750 万元；2025 年经营活动现金流量净额 -100 万元。

**观察重点**
输出被方法约束住了，并且每次都包含禁止事项与证据缺口——这是方法的价值，不是模型变强了。
更关键的是：模型**没有一次读完这个能力包**。它会自己决定先校验数据、再跑指标计算、再去读哪一份分析方法。

**这个能力包长什么样**
```
server/skills/financial-risk/
├── SKILL.md                主指令（1306 字）——入口与路由，不写细节
├── manifest.json           资源清单，同时是「可读/可执行」白名单
├── references/             4 份方法论（合计 3364 字）
│   ├── solvency.md           偿债能力
│   ├── profitability.md      盈利与收入质量
│   ├── cashflow.md           现金流
│   └── indicator-guide.md    指标口径
├── scripts/                2 个确定性程序（源码合计 6378 字）
│   ├── calculate_ratios.py   算指标 + 判阈值
│   └── validate_data.py      校验输入完整性
└── assets/                 1 个模板（825 字）
    └── report-template.md     报告输出模板
```
全量预载 = 12079 字。而一次真实分析实际进上下文的通常只有四五千字。

**现场操作顺序**
1. 先关掉 Skill，运行一次，观察输出结构是否稳定。
2. 勾选「财务风险提示分析」，点右侧「能力包」逐层看四类文件与各自体积。
3. 运行。观察时间线依次出现：索引 → 选择 → 主指令 → 挂载能力包 → **按需读取资料** → **执行脚本**。
4. 点每一条「按需读取资料」：右侧会显示读的是哪个 Skill 的哪一份、为什么读、还有哪几份没读。
5. 点「执行脚本」：重点看两个数字——**脚本源码 3917 字没有进上下文**，只有 844 字的输出回传了。
6. 回到对话末尾看那条汇总：全量预载 vs 本次实际，省了多少。再打开「详情 → 渐进式披露开销」看明细。
7. 把「选择策略」切到「自动匹配」，再问一个与财务无关的问题（例如「帮我写一段产品介绍」），
   观察时间线出现「候选均未入选，不加载主指令」。
8. 最后把「按需读取参考资料」关掉再运行：模型只能照主指令办事，读不到任何方法论，也跑不了脚本。

**两个 Skill 同时加载（建议单独演示一次）**
1. 同时勾选「财务风险提示分析」与「合同条款核对」。
2. 策略选「全部加载」，运行。时间线会连续出现两条「读取主指令」，主指令合计约 2300 字——这就是同时加载的代价。
3. 打开「选择」那一步：能看到两个 Skill 的关键词得分（全部加载模式下分数只作展示，不参与筛选）。
4. 看模型的工具调用：它会挑与问题相关的那个 Skill 去读资料、跑脚本，另一个只停留在主指令层。
5. 再把策略切回「自动匹配」，问一个纯粹的合同问题：只有「合同条款核对」入选（8 分 vs 0 分），另一个根本不加载。
   这一组对比能同时说明两件事：多选是为了让模型自己挑，全部加载是为了看清代价。

**多个 Skill 同时加载，资源怎么区分**
两个 Skill 都可能有 `references/rules.md` 这种同名文件。如果工具只有一个 `path` 参数，程序就无法判断该读哪个目录。
因此两个受控工具都要求**同时给出归属**：

```
read_skill_resource({ skill_id: "contract-review", path: "references/guarantee-clauses.md" })
run_skill_script({ skill_id: "financial-risk", script: "calculate_ratios.py", args: {...} })
```

工具仍然只有一个统一入口，归属写在参数里。应用侧会做三件事：
1. `skill_id` 必须是本次已加载的 Skill 之一，否则直接报错并列出可用值；
2. `path` / `script` 必须在该 Skill 的 `manifest.json` 白名单里；
3. 拼路径时做越界检查，禁止 `..` 与绝对路径。

同时，选择阶段就会检查**跨 Skill 的同名资源**并显示出来；当前两个演示 Skill 没有同名文件，
但机制上必须按归属寻址——这是设计约束，不是「碰巧没冲突」。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| Skill | 一个目录：`SKILL.md` + `references/` + `scripts/` + `assets/`，不是一段长 Prompt。 |
| 索引 | 启动时只读每个 `SKILL.md` 的文件头（frontmatter），正文留在磁盘。 |
| 选择策略 | 自动匹配：按问题打分，可能 0/1/多个入选；全部加载：勾选的全进上下文，用来看清代价。 |
| 主指令 | 入选后读取的 `SKILL.md`，只写「什么情况下读哪份、跑哪个」。 |
| 渐进式披露 | 先给路由，需要时才展开。库可以很大，请求只带用得上的那一份。 |
| Reference | 按需读取的方法论。读进来就占上下文，所以只读真正需要的。 |
| Script | 按需执行的程序。**只回传标准输出，源码不进上下文。** |
| Asset | 模板类资源，生成交付物时才读。 |
| skill_id | 多 Skill 场景下的资源归属。同名文件靠它区分，缺了就直接报错。 |
| ≠ 新模型 | Skill 不引入新模型，它是可复用的任务方法 + 资源 + 程序。 |

**三层披露的讲解口径**

```
第 1 层 · 索引（常驻，几百字）
   只有 name / description / keywords，用来判断「要不要用这个 Skill」

第 2 层 · 主指令（命中才读，一千多字）
   SKILL.md 只做路由：
   「涉及偿债能力时，读 references/solvency.md」
   「需要算指标时，跑 scripts/calculate_ratios.py，不要自己口算」

第 3 层 · 资源与程序（模型自己决定，按需）
   references：模型主动请求才读，读到哪份才进上下文
   scripts   ：模型只给参数、只拿输出，源码一个字节都不进上下文
   assets    ：要出报告模板时才读
```

**为什么脚本要单独讲**
大模型口算 750 ÷ 1000 大概率是对的，但它不稳定，而且换一天可能给出不同结果。
把计算放进脚本，好处是三件事同时成立：结果确定、口径统一、可以审计。
更重要的是——**模型不需要读懂那段代码**。它只要知道「有这个脚本、要传什么参数、会返回什么」。
这也是为什么脚本源码 3917 字完全不占上下文，而输出只有 844 字。

**必须主动说明的安全边界**
这一章很容易被追问「那它岂不是能在你电脑上跑任意代码」。答案必须说清楚：

- 不是开放 Bash。模型只能调一个叫 `run_skill_script` 的受控工具。
- 只能执行 `manifest.json` 里登记过的脚本，其它文件名一律拒绝。
- 参数按 schema 校验，多余字段、类型不对都会失败。
- 有超时（默认 5 秒）、有输出截断，**没有网络访问**，环境变量只给最小集合。
- 读取资料同理：只能读清单里登记的文件，路径穿越会被拒绝。

也就是说：**Skill 负责说「什么情况下该读什么、跑什么」，Harness 负责真正去读、去跑、去校验。**
这一句也是第十二章 Harness 的伏笔。

**讲师提示**：让听众亲眼看第 7 步——问一个不相关的问题，Skill 不会被加载。这比任何架构图都能说明「按需」。

**讲师提示**：不要说「Skill 帮模型省了 token 所以更聪明」。省 token 只是结果，
真正要讲的取舍是「不让模型一次接收大量与当前任务无关的指令和资料」——那才是质量问题的来源。
另外要如实说：如果一个任务需要反复往返读取，按需加载的请求次数反而更多，未必更便宜；要看整体耗时与调用次数。

## 第八章 · 结构化输出与确定性规则

> **一句话主旨**：结构是约束出来的，判断是程序做出来的

**教学目标**
理解两件容易被混为一谈的事：**约束输出格式** 与 **判断业务结论**。
前者靠请求里的 Schema + 应用侧校验，后者靠确定性规则引擎——两者都不应该交给模型「自由发挥」。

**演示问题**
星河科技（DEMO001）2024 年营业收入 1000 万元，2025 年营业收入 800 万元；2025 年总资产 1000 万元、
总负债 750 万元；2025 年经营活动现金流量净额 -100 万元。请抽取这些数据并按规则判断。

**观察重点**
页面上不会出现「模型认为风险较高」这种话。屏幕上看到的是：一段 JSON、一张校验结果、一张规则判定表，
最后才是成稿。成稿里的每个数字都能追溯到来源，因为它是**程序按模板拼出来的**，不是模型写的。

**这一章的三个环节（讲解主线）**

```
① 约束：请求里带 response_format
   端点支持时用 json_schema（严格模式）；不支持就自动退回 json_object，
   并把 Schema 写进提示词。退回这件事会在时间线里如实显示。

② 校验：应用逐字段检查
   类型、必填、额外字段、枚举、上下限。模型说「已按格式输出」不算数，
   校验器说了才算。不合格就带着错误清单让它改一次，只改一次。

③ 判定：确定性规则引擎
   资产负债率、同比变动率由代码计算，阈值比较由代码执行。
   模型连「触发还是没触发」都不参与。数据不足时输出「无法判定」，而不是默认「没问题」。
```

**现场操作顺序**
1. 直接运行。看时间线：下发 Schema → 模型返回原文 → Schema 校验 → 规则引擎 → 报告渲染。
2. 点「下发 Schema」：这是随请求发出去的约束原文，不是提示词里的口头要求。
3. 点「模型返回原文」：一段纯文本 JSON。注意它长得很规整，但**规整不等于合规**，所以还要下一步。
4. 点「Schema 校验」：逐字段的检查结论。如果模型多给了字段或把数字写成字符串，问题会出现在这里。
5. 点「规则判定」：三条规则、三个结论，标着「确定性引擎执行，非模型判断」。
6. 点「报告渲染」：说明这段回答由模板生成。然后回到对话区，对照表格逐行看数字来源。
7. 把问题改成只给部分数据（例如不给总资产），再运行：规则会显示「无法判定」，结论也会跟着变。
   这一步是为了说明「缺数据不等于没问题」。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| 结构化输出 | 用 Schema 约束模型输出成可解析的对象，而不是一段自然语言。 |
| 约束 ≠ 保证 | 约束提高合格率，但格式对不对必须由应用校验；校验不过就不能往下走。 |
| 校验器 | 一段确定性的代码，逐字段检查类型、必填、枚举与额外字段。 |
| 规则引擎 | 输入数值、输出判定，结果可复现。阈值来自制度，不来自模型。 |
| 三态判定 | 触发 / 未触发 / 无法判定。缺数据时必须是第三态。 |
| 模板渲染 | 最终成稿由程序拼装，模型只提供结构化事实。 |
| ≠ 让模型更准 | 这一章提升的是**可核对性**，不是模型能力。 |

**讲师提示**：如果有人问「这不就是限制模型吗」，回答：是，而且是有意的。
授信场景里，一个能被复核的 75%，比一段写得很漂亮的「负债水平偏高」有用得多。

**讲师提示**：不要跳过「修复一次」这个设计。真实工程里重试必须有上限，
无限重写既贵又掩盖问题；两次不过就停，比假装成功更专业。

## 第九章 · 什么是 Agent

> **一句话主旨**：给它目标、工具和终止条件，它自己决定下一步

**教学目标**
说清 Agent 与「一次问答」的本质差别：**控制流从应用手里交给了模型**。
同时说清一个常被忽略的前提——没有终止条件的循环不是 Agent，是死循环。

**演示问题**
请查一下星河科技（DEMO001）现在的工商登记状态和 2025 年财务情况，判断它的资产负债率高不高。

**观察重点**
没有人告诉它「第一步查工商、第二步查财务」。它每一轮自己判断：现在知道什么、还缺什么、要不要再查一次、
什么时候可以停。时间线上会出现多轮「判断 → 决定 → 观测」，最后以「目标达成」结束。

**循环成立的三要素（讲解主线）**

```
① 目标：用户那句话，被写进系统提示当作判定基准
② 工具：一份真实可执行的清单（工商查询、财务查询……）
③ 终止条件：
   - 模型声明 done=true（正常收敛）
   - 达到步数上限（应用的预算，不是模型的判断）
   - 连续两次工具失败（熔断）
```

**现场操作顺序**
1. 运行。看时间线：设定目标 → 第 1 轮判断 → 决定调工具 → 观测回灌 → 第 2 轮判断……
2. 点「第 N 轮」那条：右侧会显示这一轮的 assessment（它认为进展如何）、done 与否、下一步动作与理由。
3. 点「观测回灌」：这段内容被写回对话，成为下一轮的输入。这就是「它会根据结果调整」的真实机制。
4. 看结束那一条：是「目标达成」还是「步数预算用尽」。这两个含义完全不同，不要混着讲。
5. 把「步数上限」调小（能力面板里 maxToolRounds），再运行一次：观察它在没查完时被迫停下，
   结论会如实写「未能在预算内给出结论」。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| Agent | 给定目标，自主决定下一步动作，直到满足终止条件。 |
| 决策 | 每一轮输出一个结构化判断：进展、是否结束、下一步动作。 |
| 观测 | 工具返回的结果被写回上下文；下一轮决策基于它。 |
| 终止条件 | 模型自判 + 应用预算，两层都要有。 |
| 预算耗尽 | 是应用层终止，不代表任务完成；界面必须区分这两种结束。 |
| ≠ 更聪明的模型 | 同一个模型，换个控制流就能做多步任务。 |

**讲师提示**：这一章最容易讲错的地方是把「多轮工具调用」直接等同于 Agent。
区别在于**谁决定下一步**：如果每一步都是应用写死的，那还是编排，不是 Agent。

**讲师提示**：如果被问「它会不会一直转下去」，回答：不会。应用有步数上限和失败熔断，
模型自己也必须输出 done。缺任何一层都会出问题。

## 第十章 · ReAct 运行模式

> **一句话主旨**：把「想」和「做」写成文本，让循环看得见

**教学目标**
理解 ReAct 的机制：模型用文本协议轮流输出 Thought 与 Action，应用解析后执行，
再把 Observation 拼回对话。它不使用 API 层的 `tools` 参数——这一点必须讲清楚。

**演示问题**
请计算星河科技（DEMO001）2025 年的资产负债率，并说明这个水平意味着什么。

**观察重点**
时间线上能看到模型**写出来的**思考，以及每一步的动作与观测。
同时会看到这种协议的代价：格式一旦不守规矩，应用就解析不出来，界面会把原文摊开给你看。

**与原生工具调用的区别（讲解主线）**

| | 原生 Function Calling | ReAct |
| --- | --- | --- |
| 请求里有没有 tools | 有 | **没有** |
| 模型怎么表达动作 | 结构化 `tool_calls` 字段 | 文本 `Action:` 行 |
| 解析风险 | 低（协议保证） | 有，可能解析失败 |
| 可读性 | 结构化，机器友好 | 人可读，适合演示与调试 |

**现场操作顺序**
1. 运行。看时间线：第 1 步 → Thought → Action → Observation → 第 2 步 ……
2. 点 Thought：这是模型显式写出来的文本，**不是它的内部思维链**。别把两者混为一谈。
3. 点 Action：右侧展示从文本里解析出来的工具名与参数。
4. 点 Observation：这是应用执行工具后拼回去的内容，下一轮模型看到的就是它。
5. 看最后一条 Final Answer：循环终止，模型给出结论。
6. 打开「完整工具 Schema」面板会发现 `tools` 是空的——这是本章最有力的证据：
   工具不是靠 API 给的，是靠提示词约定的。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| ReAct | Reasoning + Acting：思考与行动交替，观测驱动下一步。 |
| 文本协议 | Thought / Action / Action Input / Final Answer，靠约定而非 API 保证。 |
| 解析器 | 应用侧把文本切成结构化调用的代码；解析失败是真实风险。 |
| Observation 回灌 | 把工具结果写回对话，是「看完再想」的实现方式。 |
| 解析失败 | 不是异常，是这种方案的固有成本；要显示原文，不能静默兜底。 |
| ≠ 思维链 | 展示的是模型写出来的思考文本，不是内部推理过程。 |

**讲师提示**：如果领导问「为什么不都用原生工具调用」，回答：
原生更稳，ReAct 更透明。演示和排障时看得见想什么；生产里优先用原生。

## 第十一章 · Plan-and-Execute

> **一句话主旨**：先想清楚整条链路，再按计划执行

**教学目标**
理解「规划」与「执行」分离的价值：计划是一次性产物，可以审阅、可以存档、可以在失败时被修订；
执行阶段不再重新决定做什么，只负责把计划跑完。

**演示问题**
请分析星河科技（DEMO001）2025 年度的偿债能力：先确认工商登记信息，再取 2025 年财务数据，
算出资产负债率，最后给出风险提示。

**观察重点**
屏幕上会先出现一份**计划**（目标、理由、4 个步骤、每步用什么工具、期望得到什么），
然后才是执行。这份计划可以直接贴到评审会上讨论——这是 ReAct 做不到的。

**三个阶段（讲解主线）**

```
① 规划：模型只出计划，不执行
   产出结构化 JSON：目标 / 理由 / 步骤（工具 + 参数 + 期望）
   应用校验：工具名必须真实存在，否则打回重写一次

② 执行：应用按步骤跑，不再问模型「下一步做什么」
   每步的观测结果累积起来，供后续步骤与最终汇总使用
   某一步失败 → 允许一次重规划（改的是计划，不是模型脑子里的想法）

③ 汇总：模型只对着观测写结论
   这一阶段不给工具，防止它在总结时又去编数据
   回答由「执行表 + 结论」两部分组成，执行表是程序渲染的
```

**计划里的参数怎么来（本章最硬的一点）**
规划的时候，总负债还不知道是多少——它是第 2 步查出来的。所以计划里写的是**占位符**：

```json
{ "numerator": "$2.total_liabilities", "denominator": "$2.total_assets" }
```

执行到这一步时，执行器去第 2 步的返回结果里按字段名取值，替换成 `750` 和 `1000`。
时间线上会出现一条「绑定前序结果」：左边是占位符，右边是真实值，还会写明取值规则
（唯一匹配 / 命中多条取年份最大的）。

**如果绑定失败怎么办**：这一步**不会真的执行**，而是标记为「参数引用未解析」，
然后触发一次重规划。这里刻意不做「塞个默认值」——那会把计划错误伪装成工具错误。

**现场操作顺序**
1. 运行。先看「产出计划」：4 步、每步工具与参数、规划理由。这是可以逐条质疑的。
2. 看「计划校验」：应用检查了结构与工具名。如果模型编了一个不存在的工具，会在这里被拦下。
3. 看「执行第 N 步」逐条推进：每步都有参数、观测与结果。
4. 找到「绑定前序结果」那一条：讲清「计划阶段不知道值，执行阶段才绑定」。
5. 看「汇总阶段」：模型拿到的是 4 条观测，不给工具。结论只能基于这些观测。
6. 最后看回答：先是一张执行表（程序渲染），再是结论（模型撰写）。两者分开，便于核对。
7. 对照第十章：同一个问题用 ReAct 跑一遍，比较两条路径的差别——ReAct 边走边想，
   Plan 先想完再走；前者灵活，后者可审阅。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| 计划 | 一份结构化的步骤清单，是产物而不是过程。 |
| 规划器 | 只输出计划的模型调用，不允许执行工具。 |
| 执行器 | 应用侧组件，按计划逐步调用工具，不参与决策。 |
| 参数绑定 | 用前面的观测结果填充后续步骤的参数，计划阶段只写占位符。 |
| 重规划 | 执行失败后修订剩余步骤，限一次；改的是计划本身。 |
| 执行表 | 程序渲染的步骤与结果对照表，与模型写的结论分开。 |
| ≠ ReAct | ReAct 每步都重新决策；Plan 只在开头决策一次，失败才改。 |

**讲师提示**：这一章最值得强调的不是「它能拆步骤」，而是**计划可被审阅**。
在授信场景里，「AI 打算怎么做」必须先能被看懂，才谈得上被批准。

**讲师提示**：不要说「计划一定是正确的」。计划会错——工具名会编错、参数会绑不上、步骤会多余。
所以才有校验、才有占位符失败、才有重规划。这些失败路径本身就是这一章的内容。

## 附：交互说明（讲师自己需要知道）

**1. 时间线与画布联动**
点击时间线任意一步，画布上会高亮这一步涉及的**两个节点与它们之间的连线**，箭头方向就是数据流向。
例如点「工具返回」，高亮的是「工具 → 工具处理器 → LLM」这条回传路径。
这用于回答「刚才那一步到底发生在哪里」。

**2. 同题对比**
右侧「对比」标签里选两条记录，可以并排看回答与配置差异；点「放大对比」进入全屏视图，适合投屏。
对比的前提是**同一个问题**，否则差异无法归因——页面会给出提醒。

**3. 数据与边界**
演示企业、财务数据、制度文档全部为虚构；工具调用真实发生在本机，模型调用是真实的，
但没有任何一条链路连接真实工商数据或本行生产系统。

**4. 界面可拖拽**
左栏、右栏的宽度与下方执行时间线的高度都可以用鼠标拖动分隔线调整（双击分隔线复位），
尺寸记在浏览器本地，下次打开保持不变。投影前建议先按屏幕比例调好：
讲架构时把画布放大，讲日志时把时间线拉高，讲参数时把右栏拉宽。

**5. 页面上为什么没有大段批注**
「工具调用 ≠ MCP」「Skill 四步加载」「能力包结构」这类说明，全部在本手册里，不放在界面上。
页面上只保留可操作的开关、分组标题与一两行必要提示，目的是让投影时每一屏的注意力都落在「操作与结果」上，
而不是落在讲解文字上。需要逐条对照时，用「能力包」弹层与详情面板往下钻。
