# AI 与 Agent 原理演示平台 · 教学要点

> 本文件是**讲解材料**，与演示页面完全解耦。页面只保留可操作的控件（章节、问题、能力开关、画布、时间线），
> 所有教学目标、观察重点、操作顺序、概念解释都放在这里，便于讲师按需修改、打印或单独分发。
>
> 配套平台：本地启动后访问 `http://127.0.0.1:8787`。

---

## 零、讲解主线

一句话：**先暴露局限，再引入能力，用同题对比证明差异，最后解释原理。**

```
LLM 只会读你给它的文字   →   Prompt 只改说法，不改能力
        ↓
它不记得上一轮           →   应用替它保存历史，再重发一遍
        ↓
它拿不到企业数据         →   Function Calling：模型提请求，程序去执行
        ↓
工具接入方式五花八门     →   MCP：把工具声明标准化
        ↓
内部制度它不知道         →   RAG：检索到的片段进上下文
        ↓
每次分析方法不稳定       →   Skill：把「怎么分析」沉淀成按需加载的方法
```

讲解节奏建议：每章 4–6 分钟，**先运行、后解释**。不要先讲概念再看结果，否则听众会把结果当成动画。

## 第一章 · 什么是 LLM

> **一句话主旨**：模型只看得见你发给它的文字

**教学目标**
理解 LLM 是一个「根据你提供的上下文生成文字」的模型服务，不是天然连接了所有业务系统的程序。

**演示问题**
请分析一家营业收入下降 20%、经营活动现金流为负的企业可能存在什么风险。

**观察重点**
回答通顺、结构完整，但没有任何一处引用企业级数据来源。这说明流畅不等于掌握事实。

**现场操作顺序**
1. 先不要开启任何能力，直接点击「运行」。
2. 观察画布：此刻只有「用户 → LLM → 用户」这一条通路。
3. 再追问一句：星河科技有限公司的注册资本是多少？
4. 对照两次回答，判断哪些是推断、哪些是数据。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| LLM | 根据输入的上下文，逐个预测下一个 Token 的模型服务。 |
| 上下文 | 本次调用中模型能看到的全部文字，除此之外它一无所知。 |
| 幻觉 | 当上下文里没有可靠依据时，模型仍可能生成看似合理的内容。 |

**讲师提示**：如果听众追问「它是不是偷偷查了数据库」，直接打开「详情 → 构建模型请求」，把他看到的全部内容展示出来——只有那段文字。

## 第二章 · Prompt 与 System Prompt

> **一句话主旨**：指令改变输出方式，但不新增能力

**教学目标**
理解 System Prompt 与 User Prompt 的作用边界：它改变模型「怎么答」，不改变模型「能拿到什么」。

**演示问题**
请用以下三个指标分析企业风险：2024 年营业收入 1000 万元，2025 年营业收入 800 万元，2025 年经营活动现金流量净额为 -100 万元。

**观察重点**
回答变得更规范、更克制，但模型仍然只掌握你粘贴的三个数字——指令没有联网能力。

**现场操作顺序**
1. 先在不开启 System Prompt 的情况下运行，观察回答的组织方式。
2. 打开「System Prompt」开关，点击旁边的「查看」确认内容。
3. 再次运行，对比两次回答的结构差异。
4. 注意：两次回答的数据来源完全相同。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| System Prompt | 以 system 角色发送的指令，用于约束角色、口径与输出结构。 |
| User Prompt | 用户当前这一轮的输入内容。 |
| 边界 | Prompt 是「要求」，不是「授权」，更不是「能力」。 |

**讲师提示**：可以现场删掉「不得编造未被提供的财务数据」这句，再跑一次，让听众看到输出立刻变松。这是最有说服力的一步。

## 第三章 · 上下文与多轮对话

> **一句话主旨**：模型不记得你，记得你的是应用

**教学目标**
区分「上下文」「会话历史」「长期记忆」，理解多轮对话的本质是应用把历史重新发一遍。

**演示问题**
第一轮：某企业 2024 年营业收入 1000 万元，2025 年营业收入 800 万元。
第二轮追问：那它的收入下降了多少？

**观察重点**
开关关闭时，第二轮请求里只有当前这句话；打开后，历史消息被重新发送给模型。所谓记忆，是应用在替你记事。

**现场操作顺序**
1. 保持「多轮上下文」关闭，先发送第一句话。
2. 在下方追问框输入：那它的收入下降了多少？
3. 观察模型是否知道「它」指的是哪家企业、哪两个数字。
4. 打开「多轮上下文」，重复上面两步。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| 上下文 | 本次调用实际发送给模型的全部消息。 |
| 会话历史 | 应用保存的对话记录，是否发送由应用决定。 |
| 长期记忆 | 跨会话持久化并按需读取的信息，更不是模型自带的。 |

**讲师提示**：时间线里的「构建模型请求」会写明本次发了几条消息。关闭时是 2 条（system + 当前问题），打开后变成 4 条。数字比比喻更有力。

## 第四章 · Function Calling 工具调用

> **一句话主旨**：模型提出请求，程序决定执行

**教学目标**
理解模型如何获得外部数据访问能力，以及「模型请求 / 应用执行 / 工具访问」这三者的分工。

**演示问题**
请查询演示企业A（星河科技，DEMO001）的注册资本和登记状态。

**观察重点**
模型并没有「打开数据库」，它只是输出了一段结构化的调用请求；真正查数据的是应用调用的工具程序。

**现场操作顺序**
1. 关闭工具，直接运行，观察模型是拒答、编造，还是明确说明无法获取。
2. 打开「工具调用」，并勾选「企业工商信息查询」。
3. 再次运行，点击画布上的工具节点，查看模型提出的参数与实际返回。
4. 再看时间线：模型请求 → 权限校验 → 工具执行 → 结果回传 → 生成回答。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| Function Calling | 模型输出结构化的工具调用请求，由应用解析并执行。 |
| 分工 | 模型决定请求什么，应用决定是否执行，工具负责真实访问数据。 |
| ≠ 代码执行 | 模型不能直接执行任意代码，它只能提出请求。 |

**讲师提示**：一定要点开时间线里「模型请求工具」那一步，让大家看见 `tool_calls` 只是 JSON。这是全章最关键的一屏。

## 第五章 · API 与 MCP

> **一句话主旨**：换的是接入方式，不是模型智力

**教学目标**
理解 MCP 解决的是「AI 应用与外部工具之间的标准化接入」，而不是让模型更聪明。

**演示问题**
请查询宁德时代新能源科技股份有限公司的工商登记信息：注册资本、登记状态、法定代表人。

**观察重点**
画布上会先出现 MCP Client，再出现「天眼查」这个 MCP Server 节点；回答里的统一社会信用代码、注册资本、法定代表人
都是外部实时返回的，不是模型编的。MCP 的价值在接入侧：工具清单由 Server 声明，应用无需硬编码，换工具不改代码。

**本平台已接入的真实 MCP 服务器**
| 服务器 | 传输 | 工具数 | 说明 |
| --- | --- | --- | --- |
| 演示工商库（本地） | stdio + JSON-RPC | 1 | 虚构企业，用于与真实数据对照 |
| 同花顺 iFinD · 证券数据 | Streamable HTTP | 9 | 行情、财务指标、公告与新闻检索 |
| 同花顺 · 快查企业 | Streamable HTTP | 2 | 企业工商、股权类查询 |
| 同花顺 · 法规库 | Streamable HTTP | 6 | 法规与条款检索 |
| 天眼查 · 企业数据 | Streamable HTTP | 17 | 工商画像、风险、股权、知产等 |

**现场操作顺序**
1. 先以「直连 API」方式运行一次（工具通道关闭，只勾本地函数），记住回答与画布结构。
2. 到「能力 → 工具调用」里勾选「天眼查」的 search_companies 与 get_company_basic_profile，观察画布最右列出现服务器节点。
3. 运行，点时间线里的「MCP tools/call：天眼查 / search_companies」，看参数与真实协议往返。
4. 对比两次回答：结构可能相似，但只有 MCP 这次能拿到真实工商登记数据。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| MCP | 模型上下文协议，标准化声明与调用工具、资源、提示模板。 |
| 两种传输 | 本地进程用 stdio（行分隔 JSON-RPC）；远程服务用 Streamable HTTP（POST + SSE，带会话 id）。 |
| 工具命名空间 | 平台把工具名写成 `服务器__工具`，模型看到的名字能唯一，面板也能说清工具来自谁。 |
| 别误读 | MCP 不是更强的推理能力，也不是某个厂商的私有插件。 |

**讲师提示**：这一章最容易出问题的是额度。天眼查正式期免费档每天只有 10 次调用，演示前先用「MCP 服务器 → 测试」确认
额度还在；如果被限流，答案会如实报错，不会伪造数据。切到「同花顺 iFinD」或本地演示服务器可以继续讲。

**讲师提示**：如果被问「那上 MCP 有什么意义」，回答三句：工具清单自动发现、换工具不改应用代码、权限与审计可以在一个网关收口。不要说「更聪明」。

## 第六章 · RAG 与外部知识库

> **一句话主旨**：回答的依据可以来自文档，而不是参数

**教学目标**
理解检索增强生成：把外部文档切片、建索引、按问题检索，再把片段放进上下文。

**演示问题**
怎么判断一家公司还不还得起债？请按知识库里的口径回答。

**观察重点**
这个问题在知识库里没有原句，但有一节叫「偿债能力指标」。只做词法匹配时，排名第一的是「一、总体原则」（因为命中了
"公司""判断"这些字）；换成向量检索，第一名的才是真正相关的「二、偿债能力指标」。这一屏能讲清"字面命中"与"语义相关"的差别。

**知识库当前规模**
8 篇虚构文档、61 个分块，覆盖授信政策、财务分析、行业关注点、贷后监控、担保管理、准入尽调、台账问答、风险提示规则。
每个分块都带来源文件与标题，界面上可以逐层展开：

```
server/knowledge/*.md  →  按 # 标题切分（单块 ≤ 320 字）  →  BM25 倒排索引 + 向量索引
                       →  按问题召回 TopK              →  拼成 system 消息注入
```

**现场操作顺序**
1. 先关闭知识库检索运行一次，观察模型给出的是通用经验还是本行口径。
2. 打开「知识库检索」，模式选「词法」，运行；再切到「向量」运行一次，对比 Top1 是否变化。
3. 点「查看知识库」：左侧文档树 → 展开 → 点某个分块，右侧能看到原文、分词结果（中文二元组）和向量前 10 维。
4. 在下方「检索测试」里输入同一句话，对照融合分、词法分、向量分与两个排名，再看「最终拼成 system 消息的内容」。
5. 注意回答里的口径来自这些文档，不是模型记住的。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| RAG | 检索 → 组装上下文 → 生成，参数没有被修改。 |
| 分块 | 文档按标题与句号切开，块太长会稀释相关性，太短会丢上下文。 |
| 词法检索 | BM25 统计词频与逆文档频率，只认字面重合，同义词与改写问法容易漏。 |
| 向量检索 | 用 Embedding 模型把文本映射为 1024 维向量，按余弦相似度召回，能处理同义与改写。 |
| 混合检索 | 两路分数各自归一化后加权：融合分 = 0.6 × 向量分 + 0.4 × 词法分（权重可调）。 |
| 向量缓存 | 向量按「模型 + 文本」哈希缓存到 data/index/embeddings.json，换模型自动失效，不重复计费。 |
| ≠ 训练 | RAG 不更新模型权重，改文档即改答案依据。 |

**这一章最容易出问题的地方**
- Embedding 没配好时，界面会明确显示"未配置，检索降级为词法匹配"，不会把词法结果说成语义理解。
- 换 Embedding 模型后第一次检索会重建索引，61 个分块大约 7 批请求，需要等几秒。
- 检索命中不等于内容现行或适用。演示时要主动说：文档是虚构的，真实制度要接行内知识库并做版本管理。

**讲师提示**：不要回避 BM25 的局限。主动做一次词法与向量的对比，反而更容易建立信任——银行场景里，过度承诺比能力不足更危险。

## 第七章 · Skill 与专家经验

> **一句话主旨**：把「怎么分析」沉淀成可复用的方法

**教学目标**
理解 Skill 是对一类任务执行方法的封装，且它是**按需加载**的：先只读索引，命中才读正文。

**演示问题**
根据以下数据分析企业风险：2024 年营业收入 1000 万元，2025 年营业收入 800 万元，2025 年经营活动现金流量净额 -100 万元。

**观察重点**
输出被方法约束住了，并且每次都包含禁止事项与证据缺口——这是方法的价值，不是模型变强了。

**现场操作顺序**
1. 先不加载 Skill，运行一次，观察输出结构是否稳定。
2. 打开「Skill 专家方法」，点击「加载流程」查看索引、匹配、加载三步。
3. 再次运行，对比五段式结构与「证据不足之处」是否出现。
4. 把问题改成与财务无关的一句（例如「帮我写一段产品介绍」），再运行一次，观察时间线出现「未命中，不加载正文」。
5. 思考：这和直接写一段很长的 Prompt 有什么区别。

**要讲清楚的概念**
| 概念 | 解释 |
| --- | --- |
| Skill | 目录 + SKILL.md，描述适用任务、步骤、输出结构与禁止事项。 |
| 索引 | 启动时只读 `name / description / keywords`，正文留在磁盘。 |
| 匹配 | 用当前问题在索引里做关键词打分，达到阈值才算命中。 |
| 按需加载 | 只有命中的那一个 Skill 才读取正文并注入上下文；未命中的正文一个字节都不进内存。 |
| ≠ 新模型 | Skill 不引入新模型，它是可复用的任务指导。 |

**Skill 的三步流程（讲解口径）**

```
① 索引（启动时，常驻）
   读取每个 Skill 目录的元数据：名称、适用说明、关键词
   体积很小，只占几百字节，可以全部常驻

② 匹配（收到问题后）
   用问题文本在索引里做关键词打分
   达到阈值 → 命中；未达到 → 本次不加载任何 Skill

③ 加载（仅命中时）
   读取命中那一个 SKILL.md 的正文
   作为 system 消息注入本次请求
   其余 Skill 的正文始终留在磁盘上
```

**为什么这件事重要**：Skill 会越攒越多，几十个 Skill 的正文全塞进上下文，既贵又会互相干扰。
按需加载把「方法库」和「本次请求」解耦：库可以很大，请求只带用得上的那一份。
平台的时间线会如实记录三个数字：索引多少字、命中后读了多少字、如果全量预载会是多少字。

**讲师提示**：让听众亲眼看第 4 步——问一个不相关的问题，Skill 不会被加载。这比任何架构图都能说明「按需」。

## 附：两个交互说明（讲师自己需要知道）

**1. 时间线与画布联动**
点击时间线任意一步，画布上会高亮这一步涉及的**两个节点与它们之间的连线**，箭头方向就是数据流向。
例如点「工具返回」，高亮的是「工具 → 工具处理器 → LLM」这条回传路径。
这用于回答「刚才那一步到底发生在哪里」。

**2. 同题对比**
右侧「对比」标签里选两条记录，可以并排看回答与配置差异；点「放大对比」进入全屏视图，适合投屏。
对比的前提是**同一个问题**，否则差异无法归因——页面会给出提醒。

**3. 数据与边界**
演示企业、财务数据、制度文档全部为虚构；工具调用真实发生在本机，模型调用是真实的，
但没有任何一条链路连接真实工商数据或本行生产系统。
